## lib/client.js 字节上限 + 中文转义体积（09:20 排查）

- **现象**：`lib/client.js` 里中文全是 `\uXXXX`（如 全谷→`\u5168\u8C37`），源码 `src/client.js` 是正常 UTF-8。**不是乱码 bug**，是 esbuild 默认 `charset:'ascii'` 把非 ASCII 转义；JS 引擎运行时能正确还原中文，功能无影响。
- **真实影响 = 体积膨胀**：每个汉字从 3 字节(UTF-8)膨胀到 6 字节(`\uXXXX`)。源码 14149 个中文，minify 后 4308 个进产物。
- **实测对比**（esbuild transform，minify+keepNames）：`charset:ascii`=252178B vs `charset:utf8`=228939B，**可省 23239B（≈23KB）**。
- **红线处境**：lib 现 252285B，DSH STORE 上限 262144（build.mjs 有 `>262144` 硬校验），**余量仅 9859B(3.8%)**。改 utf8 后余量→约 33KB(12.6%)。
- **方案（等用户点头）**：`scripts/build.mjs` 的 `transform()` 加 `charset:'utf8'`，重跑 `node scripts/build.mjs`。副作用评估：无功能副作用，git diff 更可读；DSH STORE 对 UTF-8 无特殊要求。
- **已执行（09:30 用户点头）**：build.mjs 加 `charset:'utf8'`，重跑成功：lib/client.js 252285→229046B（省 23239B），余量 3.8%→12.7%(33205B)。验证：`\uXXXX` 转义残留=0、4308 原始中文、峰谷文案（全谷价/按峰时价计费）正常。
- **源码发现**：当前"修改代码"版 `peakPhaseAt`（2940-2957）返回对象**已含** `nextIntoPeak`(2954) 和 `nextKind`(2955) 两字段——比"复制代码"版多了约 40 行，说明 peakPhaseAt 已被改过。`nextIntoPeak` = 布尔（下一切换点是否进峰），`nextKind` = 具体类型(peak/off/weekend)。

## 「峰谷是否按模型区分」关键机制：billingMode（10:30，用户问 codex 无峰谷是否也要手动关）

- 用户问：deepseek-V4-Pro 有峰谷→按写死方式算？codex 无峰谷→不关 peakEnabled 就还按峰谷算？
- **核心机制 `billingMode`（resolveClientPrice 2016-2111 返回）**：每个模型运行时自动归类两种：
  - `'deepseek-peak'`：命中 DeepSeek 官方主表 `prices.models`（2049/2071/2081/2108）→ 峰谷计价
  - `'flat'`：第三方 `prices.providers[xx].models` 目录命中（2076）、本地模型(2043)、未命中(2110)→ 一口价
- **2217 行关键闸**：`tierFor(entry, now, { ...peak, enabled: resolved.billingMode === 'deepseek-peak' && peak.enabled })` —— 峰谷只对 billingMode=deepseek-peak 生效；codex 等第三方被 `&& billingMode==='deepseek-peak'` 强制压成 false，走 base 一口价。

- **isPeakHour 1818-1830**：`getUTCHours()` 判断当前小时是否在 windows 区间；周末(weekendZoneAt)直接 false。
- **结论（回答用户）**：① deepseek-V4-Pro=官方主表→自动峰谷，每次对话按"当前时刻峰/谷"选价，对。② codex=第三方目录→自动 flat 一口价，**即使 peakEnabled 开着也不按峰谷算**，用户第二个假设错。③ 推论：peakEnabled 开关只对 DeepSeek 官方模型账本生效，对 codex 等第三方渠道完全无效（开/关都 flat）。
