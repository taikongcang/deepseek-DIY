# 通用开源项目贡献指南（参考读物）

> **这是给人看的参考读物** —— 用来学习"一个成熟的开源项目，贡献流程长什么样"。
> **AI 不要读这份文件。** 本仓库自用的贡献与改动规则在 [`../CONTRIBUTING.md`](../CONTRIBUTING.md)。

---

## 一、贡献者有几类

一个开源项目的"贡献"远不止写代码。按投入成本从低到高：

| 角色 | 做什么 | 需要什么 |
|---|---|---|
| **使用者** | 用、反馈问题、写教程、翻译文档 | 会用就够了 |
| **问题报告者** | 提交可复现的 bug、提出功能建议 | 会描述现象、会复现 |
| **文档贡献者** | 补文档、修错别字、写示例 | 会写清楚的句子 |
| **插件/生态作者** | 基于项目的扩展点做第三方扩展 | 会用项目的扩展机制 |
| **代码贡献者** | 修 bug、实现功能、写测试 | 会读项目源码 + 会跑测试 |
| **维护者** | 评审、合并、发版、治理 | 长期投入 + 判断力 |

**关键认知**：**"提一个好 issue"的价值常常不低于"提一个 PR"**。多数项目缺的不是代码，是清晰的复现步骤。

## 二、发现问题：issue 怎么写

一个好的 bug 报告包含四件事：

1. **环境** —— 操作系统与版本、项目版本、安装方式（安装包 / 源码 / 包管理器）
2. **复现步骤** —— 一步步，能让别人照着重现。**能稳定复现 = 问题解决了一半**
3. **期望 vs 实际** —— "我以为会发生 A，实际发生了 B"
4. **证据** —— 报错原文、日志、截图。**贴原始文本，不要只转述**

功能建议则要讲清：**你遇到的问题是什么**（而不是直接跳到"所以你应该加个 X 功能"）。因为维护者往往能看到比你的方案更简单的解法。

**常见反面例子**：
- "用不了，快修"（没有环境、没有步骤）
- "某某软件有这个功能，你们也加一个"（没说清你的真实需求）
- 把多个不相关的问题塞进一个 issue

## 三、提交代码：PR 流程

标准流程：

```
fork → 建分支 → 改代码 → 跑测试 → 提交 → 推送到你的 fork → 开 PR → 按评审意见修改 → 合并
```

**几条硬经验**：

- **一个 PR 只做一件事**。修 A 的顺带改了 B，评审会很难受，也容易被要求拆开。
- **先开 issue 讨论，再写大 PR**。大改动没先对齐方向，可能白做。
- **提交信息写"为什么"，不只写"做了什么"**。三个月后回头看，`修复超时` 毫无信息量；`卸载时 pnpm 子进程不退出导致界面永久等待，改为加超时并强制终止` 才是有用的历史。
- **不要让 CI 红着**。多数维护者不看红 CI 的 PR。
- **改动保持最小**。不顺手重构、不重排格式 —— 那会让 diff 淹没真正的改动。
- **新功能自带测试**。测试是"这个行为被锁住了"的凭证，不是额外负担。

## 四、代码与文档规范

### 代码

- **跟随项目既有风格**，不要引入你个人偏好的风格。这是最常被拒的原因之一。
- **命名要说明意图**：`retryCount` 比 `n` 好。
- **错误处理要明确**：失败时是抛错、返回 null、还是重试？不要"静默吞掉"。
- **避免过度抽象**：为一个用例引入三层间接，比重复代码更糟。

### 文档

- **改代码时同步改文档**：行为变了、文档没变，等于给下一个人埋坑。
- **双语项目要保持两侧同步**：有些项目会用工具校验（例如记录每个文件的哈希），改一侧必须改另一侧并更新记录，否则校验会红。
- **写清楚前置条件**：读者不知道你的隐含假设。

## 五、评审与合并

维护者评审时会看：

- **这个改动解决的是真问题吗？**（还是"我感觉应该这样"）
- **有没有更小的改法？**
- **会不会破坏别的用法？**（向后兼容）
- **测试覆盖了吗？**
- **维护成本**：以后每次升级都要重做一遍吗？

被要求修改时：

- **不要情绪化**。评审针对代码，不针对人。
- **不确定就提问**，别猜着改。
- **改了之后回一句**，让评审者知道可以再看（很多 PR 死在这里：作者改了但没说，评审者以为还没动）。

**"维护成本"这一点最容易被新手忽略**：一个改动如果让项目以后每次跟随上游升级都要重新适配，那它的隐性代价可能远大于眼前收益。

## 六、行为与冲突

成熟项目通常有一份 **行为准则（Code of Conduct）**，规定：

- 参与者应保持友善、包容，不因年龄、性别、种族、宗教、经验水平等区别对待他人；
- 不接受的行为：人身攻击、骚扰、歧视性言论、公开他人隐私等；
- 违规的处理路径：向指定邮箱/人员举报 → 维护者评估 → 视情节警告、临时封禁或永久移出。

它的作用不是"形式主义"，而是在**有陌生人协作时，把底线写清楚**。个人项目、无外部贡献者时通常不需要。

---

## 七、新手最容易踩的坑

| 坑 | 说明 |
|---|---|
| 改了一堆不相关的东西 | 评审成本爆炸，容易被要求全部拆开重来 |
| 不给复现步骤 | 维护者无法判断，只能来回追问 |
| 直接提方案不提问题 | 可能解决了错误的层面 |
| 不跑测试就提交 | CI 红了，评审直接跳过 |
| 忽略"维护成本" | 短期解决了问题，长期让项目背上债务 |
| 把 review 意见当人身攻击 | 沟通成本骤升，PR 容易僵死 |
| 改了代码没改文档 | 下一个人踩坑 |
| 只改双语文档的一侧 | 一致性校验会失败，或另一语种读者被误导 |
